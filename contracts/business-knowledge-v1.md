# Business knowledge v1 companion note

This is a first-slice wire contract for registration and a typed business brief. It is not a deployed service, database migration, or general knowledge ontology. It reuses the existing intake shape: business name, services, location/service area, differentiators, verified trust evidence, audience motivations, concerns, conversion goals, voice, and prohibited claims. Each field has an explicit string or list-of-strings value shape. A later contract version can add typed offerings or claims once their producer and consumer boundaries are agreed.

V1 carries evidence references, locale, and AI observation provenance but does not define question or research-evidence entities or future provider APIs. Evidence retention and deletion continue to follow the existing source/tenant retention obligations; this schema does not authorize indefinite retention or provider access.

## Identity and registration

`project_registration` carries the HelloAda workspace ID, a namespaced `externalProjectId` (`<origin.system>:<origin.externalId>`), the originating system/record, and an idempotency key. The schema restricts `origin.system` to a colon-free namespace; `externalId` may contain colons. This makes the separator unambiguous, so `(workspace, system, externalId)` maps injectively to `(workspace, externalProjectId)`. `project_registration_result` returns the canonical `{workspaceId, projectId}` pair: `projectId` is the CrawlSEO server ID and `externalProjectId` remains the caller's stable external ID. The current `Project` model already has unique `(workspaceId, externalProjectId)`; registration uses that identity and does not create a parallel project map. The equivalent origin uniqueness is `(workspaceId, origin.system, origin.externalId)`. Registration first checks its durable receipt: an identical retry returns the stored result, while reuse of the key with a different normalized request returns `IDEMPOTENCY_CONFLICT`. A new key then resolves/creates the unique Project origin; same origin with conflicting registration data returns `ORIGIN_CONFLICT`. Every registration writes a receipt containing the request hash and original result, scoped by workspace, operation, and idempotency key. A public domain is optional metadata and is not an identity key. Legacy Google/domain provisioning remains a separate site-attachment flow.

Credentials are minted by the owning service, bound to one workspace/project pair and an explicit permission list, and checked on every operation. A request whose project scope differs from its credential's scope returns `NOT_FOUND` for project/document reads and writes so that scope errors do not reveal another project's existence. Missing/invalid credentials return `UNAUTHENTICATED`; authenticated but insufficient permissions return `FORBIDDEN`.

## Writes, acceptance, and reads

Every credential is bound to a server-side project ID. For each scoped document, a write checks the credential's workspace/project binding and permission, then the idempotency receipt, then `expectedRevision`, then validates and commits. The idempotency namespace is `(projectId, operation, idempotencyKey)` as in the existing connector receipt pattern; the normalized request fingerprint covers the complete request, including document ID, reason and changes (the principal is already constrained by the project credential). An identical retry returns its stored original result even if the document has since advanced; the same key with a different body returns non-retryable `IDEMPOTENCY_CONFLICT`. A new key with a stale `expectedRevision` returns retryable `REVISION_CONFLICT` and the current revision. Successful content writes append a new immutable revision.

Acceptance is an explicit `document_accept` operation, authorized to an owner or workspace admin and guarded by the exact current `expectedRevision` plus an idempotency key. It records an immutable acceptance event and pins `acceptedRevision` to that current revision; it does not rewrite the content or invent another content revision. A later content write creates a new working revision and preserves the prior `acceptedRevision`. A later acceptance advances the pointer but keeps earlier acceptance events. A read without `revision` selects the latest working revision or, for `view: accepted`, the latest accepted pointer. A read with an explicit `revision` returns that exact immutable revision; `view: accepted` additionally requires that revision to appear in the document's acceptance history, so an older accepted brief remains readable after the pointer advances. A document that has never been accepted has no accepted-view result. Consumers must enforce `acceptedRevision <= revision`; when `state` is `accepted`, the pin must equal `revision`.

## Provenance and publication use

Each field fact carries origin system, origin record and source revision/hash token, actor type/ID, evidence reference, observed time, recorded time, and status. `originRevision` accepts an integer, opaque string token, or null when the source does not expose a revision; adapters must not fabricate one. `recordedAt` and `observedAt` are separate timestamps. Status distinguishes owner/admin confirmation, advice, assumptions, verification, disputes, deferral, non-applicability, and unknowns. These describe where a statement came from and its evidential state. `publicationUse` is a separate policy decision (`approved`, `internal_only`, `prohibited`, or `unknown`); owner confirmation or verified provenance does not itself grant publication permission.

## Persistence and compatibility

The smallest physical shape that preserves these guarantees reuses `Project.id` and its existing unique `(workspaceId, externalProjectId)` identity; a document head keyed by `(projectId, documentId)` holding current and accepted revision pointers; immutable document revision rows keyed by `(projectId, documentId, revision)`; immutable acceptance events keyed by `(projectId, documentId, acceptedRevision)`; document receipts unique on `(projectId, operation, idempotencyKey)`; and required registration receipts unique on `(workspaceId, operation, idempotencyKey)`. Receipts retain request hash and original result. Store credential principals/permissions in the existing auth system rather than embedding bearer secrets in documents. This is a design minimum, not a prescribed Prisma migration.

V1 keeps the existing SiteProfile and connector context as compatibility projections. During transition, their current writers remain authoritative for their existing fields until each producer is explicitly moved. The shared contract is authoritative only for a migrated field after its writer and readers use the same revisioned record; dual writes must not silently choose a winner. Backfill preserves legacy IDs, values, and hashes as provenance. A field-level cutover records the source and time, and consumers pin the exact accepted revision they used. No existing production authority changes merely because this contract is reviewed.

The schema documents wire shape; cross-field lifecycle and stateful conflict outcomes are checked against the same fixtures by `tests/knowledge-contract.test.ts` and `check_business_knowledge_v1.py`.
